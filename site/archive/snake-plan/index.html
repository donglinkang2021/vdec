当时建议按以下顺序验证：

  1. 平衡左、直、右的危险位置，并让尾巴在图上可辨认。
  2. 将 plan 预算从 128 提高到 512、1024，检查策略是否完整。
  3. 比较当前截图的直接作答与逐题 CoT，定位视觉能力差距。
  4. 用 20–30 个配对 seed 做闭环，检查食物数、碰撞和延迟。

因此，这组规划后的提升，目前无法区分“模型学会了避险”和“模型变得更偏爱左转”。只看危险截图也不足以解决这个问题，还必须平衡危险动作的位置。 四种旋转会改变绝对朝向，却保持相对左转、右转关系，所以旋转扩增没有消除这个偏差。局面生成代码（仓库内证据：../../src/vdecision/benches/snake/archive/environment.py）

你关心的安全率与碰撞召回，核心区别在于它们回答不同问题：

指标回答的问题单独使用时的漏洞
碰撞判断准确率所有“状态＋动作”中，判断对了多少？安全样本多时，全部回答安全也能高分
危险召回率真正会撞的动作中，识别出了多少？全部回答危险可以拿到 100%
危险误报率真正安全的动作中，多少被误判危险？需要与危险召回一起看
动作安全率最终选出的动作，有多少不会立即撞？固定动作可能利用数据偏差拿高分

报告中 choice_boxed + no_plan 的碰撞题，共有 264 次真实安全、24 次真实危险；全部答安全，就得到 91.67% 判断准确率、0% 危险召回率。这说明它在该测试条件下没有检出危险。报告 §3.4

还要区分“会判断危险”和“会选动作”：模型可能把三个动作都判断正确，最终仍选错；也可能不会解释碰撞，却碰巧选到安全动作。因此，碰撞判断与实际动作选择应分别测量。

我会按下面五步推进。

  1. 先做一个小而有区分度的安全 benchmark。

    首轮建议用 90–150 个不同的基础局面，按三个动作中有 3、2、1 个安全动作分层采样。完全无路可走的局面单列，用于诊断，不混进“能否避免碰撞”的主指标。

    关键设计是让左转、直行、右转都充分出现为危险动作，也都出现为唯一安全动作。覆盖墙角、撞身、尾巴腾空、食物诱导进入危险方向等情况。全安全局面仍有价值：它们可以测危险误报，以及模型是否追逐食物。

    我最建议加入成对的局面：保持大部分画面相同，只改变一个会影响决策的因素。例如，把前方障碍移开；保持身体占用格不变但改变可辨认的尾巴位置；移动食物使应选动作改变。检查模型是否随关键视觉变化改变判断，比单看总分更接近你想证明的视觉能力。

    每次报告至少包含：危险召回、危险误报、危险局面的动作安全率、三个动作分别的表现，以及完整安全动作集合的判断正确率。多个动作都安全时，允许多个正确答案，不要人为指定唯一“正确动作”。

    开发集和测试集按基础局面或来源轨迹划分，同一局面的旋转、镜像和成对变体放在同一侧。排列次数和旋转次数用于测一致性，不能当成新增独立样本。

    扩集前还需要解决一个观测问题。 当前所有蛇身格使用同一种颜色，蛇尾没有标记。我构造了两个通过当前合法性校验的状态，截图哈希完全相同，但左转在一个状态进入即将腾空的尾巴，在另一个状态撞到身体。这意味着密集身体局面中，单帧截图可能不足以确定标签。渲染与碰撞规则（仓库内证据：../../src/vdecision/benches/snake/archive/environment.py）

    如果你先研究单帧的一步安全，建议给蛇尾增加视觉标记；后续涉及身体移动顺序和长期规划时，再考虑连接线或历史帧。这是让输入包含必要信息。

  2. 把 plan 加长，但以“计划完整”为目标，不以 token 数更多为目标。

    报告的 144 份 plan 全部在 128 token 截断，所以现在确实不足以评价完整策略的效果。报告 §3.5

    可以先做一个很小的生成检查：保持提示和 thinking 不变，比较 plan 上限 128、512、1024，记录实际长度、停止原因、是否完成以及是否包含明确决策规则。thinking 是否被强制截断也要单独记录。

    我建议把两个问题分开：先固定提示检查预算是否足够，再改提示要求简洁、完整的决策规则。否则长度和提示同时变化，很难解释收益。

    完整性检查通过后，在新安全集上比较：

    条件想验证什么
    无 plan原始快速决策能力
    人工写好的简洁通用规则清楚的策略上下文是否有帮助
    无 thinking 生成的完整 plan直接生成策略的效果
    thinking 后生成的完整 plan，仅保留 plan推理生成的摘要是否有用
    同一份 thinking＋同一份 plan保留推理正文是否进一步帮助

    人工规则应在开发集上确定，不针对测试局面写答案。它的价值是提供一个质量较明确的对照：如果它有效而模型生成的 plan 无效，下一步应改善计划生成；如果都无效，就要关注模型是否能把规则应用到截图上。

    full 与 plan_only 的比较只能回答“保留这段推理上下文有没有帮助”；它同时改变了内容和上下文长度。出现可靠收益后，再补长度匹配等进一步消融。

  3. 增加真正看当前局面的 CoT，用它定位能力缺口。

    现有共享规划只看外观示例，因此它测试的是“通用策略能否帮助快速决策”。它没有回答：同一张测试截图，给模型更多推理时间，能不能做对？

    代码中名为 per_step_cot 的分支，生成规划时仍传入 reference_image()，需要另行实现针对当前截图的推理条件。对应代码（仓库内证据：../../src/vdecision/benches/snake/episode.py）

    最有信息量的诊断是这四组：

    输入直接回答针对当前局面推理后回答
    当前截图目标快速策略潜在的视觉 teacher
    真实结构化状态，仅作诊断减少视觉理解负担检查规则推理能力

    如果结构化状态明显更好，应重点查视觉定位、空间关系和身体识别；如果当前局面 CoT 明显优于直接回答，就出现了值得压缩或蒸馏的能力差距。如果 CoT 也识别不了危险，暂时不能把它当可靠 teacher。

    结构化真值只放在明确标注的诊断条件中，主方法始终按目标使用截图。

  4. 尽早跑小规模闭环，检查静态收益能否转化为会玩。

    仓库已经有 episode 入口，可以在新安全集有初步结果后，选两三个方法跑 20–30 个配对游戏 seed 做探索，不必等待大型 benchmark 完成。现有入口

    主要看每局吃到的食物数、存活步数、可避免碰撞、重复状态比例，以及每步延迟的 P50/P95。固定左转可能在局部循环，因此存活也要与进食一起看。当前 128 步上限适合初测；若大量方法达到上限，再延长，否则容易把截断当成长期成功。

    基线保留随机、固定动作，并增加使用环境真值的简单避撞贪心策略作为能力参照，明确其额外信息来源。

    “快速”需要在连续变化的截图上测量。报告的静态矩阵反复使用相同图片，缓存命中率不能直接代表闭环；输出只有一个 token，也不意味着视觉编码和输入处理免费。共享规划生成成本、模型启动成本与稳定运行时每步成本应分别报告。

  5. 等 teacher 优势可信后，再接入 vdistill。

    我按实际目录 ../vdistill 理解你的长期规划。那里已有 private skill prompt 的蒸馏和 closed-book replay 相关实现，可以作为连接点；多模态输入、动作标签和闭环采样仍需要专门适配。现有蒸馏模块（仓库内源码）

    最小训练验证可以是：teacher 使用当前局面 CoT 或经验证有效的策略上下文，student 只看截图并输出动作；先训练动作选择与安全判断，再检查是否保持低延迟。这个方向与把 System 2 的输出能力蒸馏到无需中间推理的 System 1 一致，但迁移到 Snake 的收益需要实验确认。相关研究

    后续数据应加入 student 自己玩到的失败局面，再补标注或 teacher 判断。因为动作会改变下一步看到的状态，只在固定截图上训练容易漏掉部署时的分布变化；这是 DAgger 所处理的问题。DAgger 原论文

就下一轮实际投入而言，我会先选 一个模型、当前两个 boxed 读出方法、一个主后端。优先完成安全集和完整 plan 检查，再加入当前局面 CoT 与小规模闭环；关键差异出来后，用第二个模型和另一后端复核。

下一轮最值得拿到的证据是：在固定动作无法取巧、截图信息充分的新局面上，完整规划或当前局面 CoT 能稳定减少可避免碰撞；随后，这种优势能被保留在快速闭环决策中。 这份证据会直接决定你接下来应该优化提示、补视觉训练，还是开始做 teacher→student 蒸馏。
